# Standalone CBOM download

Use `GET /api/exports/cbom?scan_id=42` with the normal authenticated API session. Omitting scan_id selects the latest completed scan. Existing `/api/cbom` pagination and `/api/cbom.csv` behavior remain unchanged. The user subsequently authorized the CBOM download integration: the `Full JSON` button now downloads this endpoint using the displayed scan's metadata id, including completed empty scans. CSV uses its existing endpoint. Download failures show a retryable alert. See [integration verification](integration-verification-2026-10-08.md).

Successful response: `application/vnd.cyclonedx+json`, attachment filename `ecdat-cbom.json`, `X-Exported-Count`, SHA-256 document ETag and `Cache-Control: no-store`. Each export has its own UUID serial and version 1. It is a fresh document, not a persisted risk-edit revision. `ecdat:scan:result-version` identifies scanner results only.

The export includes every stored finding from one selected completed scan, including empty scans. It reads scan metadata, finding fields, evidence, risk scores and provenance in a single joined database SELECT. There is no count-then-paginate assembly and no subsequent database fetch during serialization. SQLite and PostgreSQL provide statement snapshots; unsupported dialects receive 503. SQLite concurrency is covered by a real separate-writer WAL test. PostgreSQL execution has not been rehearsed in this stage.

Bounds: 10,000 findings and 32 MiB serialized JSON. Exceeding either returns 413, with no truncated document. A missing scan returns 404; an unfinished/failed/cancelled scan returns 409. Invalid generated schema data returns 500 instead of claiming a valid export. A completed scan with failed files may export its stored inventory; metadata reports in-scope/scanned/failed counts, coverage and blind spots. Complete export means all stored findings, not complete repository discovery.

Mapping: one `library` component per stored finding, with unique `ecdat:asset:<database-id>` bom-ref and algorithm name. This preserves the existing ECDAT inventory/property representation; algorithm operations are not thereby standardized library identities or native cryptographic assets. `ecdat:asset:<field>` properties retain non-null AssetResponse fields, including location, evidence kind/quality, safe structured evidence, confidence, risk context/provenance, reasons, recommendation, parser version and source span. Structured values use JSON strings; scalar values use strings. Missing key parameters remain omitted rather than invented. Database id is represented in bom-ref, and scan id in metadata. Raw source fields and known secret/private-key fields/content are redacted through the existing conservative policy before serialization. Redaction is not proof against every arbitrary secret representation.

The native `cryptographic-asset`/`cryptoProperties` mapping remains a separately planned extension. No native certificate/protocol relationships or dependencies are invented. Metadata explicitly identifies this limitation. The validator additionally rejects duplicate identifiers and dangling dependency refs; the current exporter emits no dependency edges.

Validation uses unmodified official CycloneDX 1.6 schema files and their SPDX/JSF references pinned with source URLs, commit and checksums under `schemas/cyclonedx/1.6`. A local registry disables network schema retrieval. `scripts/validate_schema.py --cbom --file download.json` checks a saved document offline. Schema acceptance, finding completeness, concurrency and redaction are tested separately. Acceptance does not establish detector accuracy, native cryptographic semantics or enterprise readiness.

Source: [official schema repository](https://github.com/CycloneDX/specification/tree/55343ba19dee1785acf1ce9191540d5fd7b590db/schema). Validator: [jsonschema 4.26.0](https://pypi.org/project/jsonschema/4.26.0/). Docker includes the pinned schemas; its existing lockfile gains only the new validator dependency tree with hashes. No database migration is required.
